# RFC — La déclaration d'une ressource en 1.0

Statut : implémentée dans `react-resource-view` 1.0.0.
Liens : [guide de migration](../../MIGRATION-1.0.md), [liste des changements en données](../../migrations/1.0.json).

## 1. Le but

Une déclaration se comprend en la lisant une fois, sans ouvrir la documentation.
Chaque décision ci-dessous a été tranchée avec la grille du ticket :

1. une notion = un seul endroit ;
2. on ne propose que ce qui a un effet ;
3. le nom dit ce que fait l'option ;
4. des défauts qui marchent ;
5. les erreurs se voient en dev, avec le correctif ;
6. le typage sert de doc ;
7. casser seulement si ça améliore nettement la lecture.

## 4. Les choix, axe par axe

### 4.1 Permissions

- Forme : `"all" | "readonly" | Action[] | Partial<Record<Action | "export", Permission>>`
  comme proposé. `"readonly"` = `list`, `read`, `export`.
- Tout est autorisé par défaut, export compris ; le bouton d'export n'apparaît
  que si la ressource a un `path` **et** que son dialecte décrit un export
  (pas de bouton sur une ressource `storage: "local"`).
- Une fonction reçoit `{ action, item, context }` et peut répondre par une
  promesse. Une erreur vaut refus (et un `console.warn`).
- Cache : une `Map` par contexte de vue, vidée quand ses données sont
  rechargées. Une liste de N lignes pose N questions par action, quel que soit
  le nombre de rendus (testé). Tant qu'une réponse asynchrone n'est pas là,
  l'action n'est **pas** proposée : on n'affiche jamais un bouton pour le
  retirer ensuite. Seules les réponses **asynchrones** sont gardées : une
  règle synchrone est reposée à chaque rendu, pour suivre ce qu'elle lit (le
  rôle de l'utilisateur, l'enregistrement). Hors de tout contexte de vue,
  chaque composant garde son propre cache.
- Le tableau Kanban ne déplace ni ne laisse glisser une carte dont
  l'enregistrement ne peut pas être mis à jour.
- Routes : `ViewResourceContextProvider` évalue la permission de l'action
  affichée ; quand c'est une fonction et que la route vise un enregistrement,
  il attend l'enregistrement (chargeur) — sauf s'il n'a pas pu être chargé :
  la règle est alors posée sans lui —, puis affiche le `forbiddenFallback`
  du scope, sinon celui de la configuration, sinon « Access denied ».
- `permissionResource(resource, action, { item, context })` renvoie
  `boolean | Promise<boolean>` ; `usePermission(action, item?)` et
  `useAllowedActions(actions, item?)` sont les hooks.

### 4.2 `behavior`

Comme proposé. Deux précisions :

- `afterSave` par défaut : `close` dans un dialog ou un drawer, `stay` sur une
  page — ce qui reproduit 0.15 (après une création sur une page, `stay` passe
  sur la fiche créée). `close` sur une **page** ramène à la liste : c'est un
  comportement nouveau (0.15 ne faisait rien).
- Le codemod supprime `afterSave: "close"` à côté d'un `open: "dialog"|"drawer"`
  (c'est le défaut) : `POPUP = { behavior: { openIn: "popup", closeAfterUpdate: true } }`
  devient `{ open: "dialog" }`.

### 4.3 `view` / `views`

Comme proposé : racine = commun, `views.<action>` typé par action, fusion
profonde `défauts lib → configureResourceView → racine → action → layout`.
Règles de fusion (`src/definition/mergeDefinition.ts`) : objets littéraux
fusionnés clé par clé, tableaux et fonctions remplacés, `undefined` ignoré,
`false`/`null` gardés — c'est ainsi qu'on retire (`inputs: { notes: false }`,
`components: { top: null }`).

### 4.4 Layouts

Comme proposé (`layout.table/cards/board/calendar/timeline/split/items`), plus
`layout.custom` pour les layouts maison. Les options de champ sont typées
`keyof Item` : à l'intérieur de `createViewResource<Task>(…)`, TypeScript infère
`Item` depuis le type de retour attendu (essayé sur TS 6 : « Did you mean
"status"? » s'affiche) ; un layout construit seul se type avec
`layout.board<Task>(…)`. `NoInfer` empêche qu'une faute de frappe _devienne_
le type.

### 4.5 API, stockage, hooks

Comme proposé, sauf la forme du contexte des hooks (voir écarts).

### 4.6 Titres, libellés

Comme proposé. Le titre dérivé est celui de 0.15 (« Create — Tasks »,
« Edit — Tasks », « Delete — Tasks », le nom pour la liste et la lecture).

### 4.7 Composants, 4.8 sous-vues, 4.9 pagination et filtres

Comme proposé, avec les écarts ci-dessous.

### 4.10 Scope, menu, configuration

- Le scope lie chaque ressource de `resources` quand il se charge.
  `resource.scope` devient le scope affiché quand la ressource y est listée,
  sinon le premier qui l'a listée : une ressource partagée entre deux scopes
  fait ses liens dans celui où l'on est.
- `menu: "auto"` liste `resources` ; une liste explicite mêle ressources, liens
  et groupes. Les entrées sont construites au chargement du scope, dans son
  nom : c'est ce qui rend `createItemMenuWithResource({ scope })` inutile.
- Sans `scopes`, `configuration.resources` est lié au scope des paramètres ou
  au `defaultScope` (c'est le cas du site de doc).
- `configureResourceView({ defaults })` peut être appelé après la déclaration
  des ressources (les imports s'exécutent avant le corps de l'application) :
  les ressources déjà construites sont résolues à nouveau.
- Registre typé des scopes : étudié, **pas fait**. Une ressource ne nomme plus
  son scope, donc la faute de frappe que visait le registre (`scope: "admn"`
  dans une ressource) n'existe plus ; il resterait `defaultScope` et
  `generateLink({ scope })`, qui gagneraient à être typés, mais l'augmentation
  de module (`declare module "react-resource-view" { interface Scopes … }`)
  ajoute une notion à apprendre pour un gain faible. À rouvrir si le besoin
  apparaît.

### 4.11 Types publics

`ResourceDefinition<Item, Write>` (ce qu'on écrit) et `ViewResource<Item, Write>`
(ce que la lib construit, avec `views` résolues et `permissions` normalisées).
Les nouveaux types n'ont pas de suffixe `Interface` (`ListViewDefinition`,
`BoardLayoutOptions`, `Quota`, `Permission`…). Les types d'exécution existants
qui ne changent pas de sens gardent le leur (`RowInterface`,
`ListComponentPropsInterface`, `ViewResourceContextParams`…), pour ne pas casser
sans gain de lecture (principe 7).

### 4.12 Validation en dev

`src/definition/validateDefinition.ts`. Active si `process.env.NODE_ENV !==
"production"` (remplacé par tout bundler React) ou si le port `isDev` est vrai ;
rien en production. Toutes les erreurs d'une déclaration sont levées **en une
fois** (`Error` listant chaque chemin) ; un titre identique au titre dérivé
n'est qu'un `console.warn`. Les clés 0.x et leurs réécritures viennent de
`migrations/1.0.json`, recopiées dans `src/definition/legacyKeys.ts` pour ne
pas embarquer toute la liste dans le bundle (un test vérifie qu'elles restent
identiques).

## 5. Écarts par rapport au ticket, et pourquoi

1. **`components.list/row/item` ne sont pas proposés à la racine ni par
   action, seulement sur les layouts.** En 0.15 ils étaient écrasés par tout
   variant (chaque fabrique fixait les trois) : déclarés à côté de
   `viewVariants`, ils n'avaient aucun effet. Principe 2. Le codemod les
   déplace dans un `layout.table({ components })` quand la vue n'avait pas de
   variants (seul cas où ils agissaient).
2. **`tabs.aside`** : nom donné à la colonne de gauche des sous-vues
   (`subViewResource.viewComponent`), que le ticket ne nommait pas.
3. **`fields` sur les layouts** (ajout). La fusion profonde rend la forme 0.15
   « un form de layout qui remplace celui de la ressource » impossible à
   exprimer sans lister des `false` ; une liste de champs se lit mieux. Indice :
   la doc du dépôt écrivait déjà `tableViewOptionFactory({ columns: [...] })`,
   une option qui n'existait pas.
4. **Le contexte des hooks garde la forme `{ viewResourceContext }`** (celle
   que reçoivent les méthodes du repository) plutôt que `{ context }` : une
   seule forme pour les hooks et le repository, et la migration de
   `preCreate(data, ctx)` reste automatique.
5. **Pas de `storage` exigé pour une ressource « page »** (`components.view` à
   la racine ou sur la liste) : l'écran `overview` du playground n'a pas de
   données, et lui demander un stockage serait faux. En production, une
   ressource sans source de données échoue à chaque appel avec un message, au
   lieu de basculer sur `localStorage`.
6. **Codemod et permissions.** Une déclaration 0.x qui nommait au moins un
   `canXxx` est réécrite avec les refus qu'elle impliquait (rien ne change à
   l'écran). Une déclaration qui n'en nommait **aucun** (l'exemple du README)
   n'en reçoit pas : elle passe au défaut 1.0 (tout autorisé) et le codemod la
   **signale** (RV1-PERM-002 dans le rapport). Écrire des refus partout aurait
   figé le bug que le ticket corrige, et rendu le codemod non idempotent.
7. **`list` n'est refusée par le codemod que si `canList` l'était.** En 0.15,
   `canRead: false` ne cachait que les boutons « voir » et le lien de retour :
   la page liste s'affichait. Avec la protection des routes, traduire
   `canRead: false` en `list: false` aurait fermé des listes qui marchaient.
8. **`limit` → `quota` partout**, y compris le paramètre d'exécution `limit`
   de `ViewResourceContextParams`, `useLimit` → `useQuota` et les types : une
   notion, un nom.
9. **Les noms d'exécution liés au layout restent** (`viewVariant` dans le
   contexte, `viewVariantId` dans les paramètres, `?variant=` dans l'URL) :
   les renommer cassait les liens partagés sans rien changer à la
   déclaration.
10. **`create-view-variant` garde son nom** (principe 7), avec l'alias
    `create-layout` ; il écrit désormais `heatmapLayout.tsx` avec
    `layout.custom()`.
11. **`BulkActionInterface.onAction` renvoie `unknown`** (au lieu de
    `void | Promise<void>`) : la tâche du playground renvoie
    `Promise.all([...])`, ce que l'ancien type refusait — c'est en partie ce
    qui obligeait à typer `BOARD_BEHAVIOR` en `object`.
12. **`encodeIri` accepte un identifiant numérique.** Les boutons apparaissent
    désormais par défaut ; sur Strapi et Supabase leur lien passait un `id`
    numérique à `encodeIri`, qui plantait (`startsWith` sur un nombre). Ce bug
    existait en 0.15 mais restait caché derrière le refus par défaut.
13. **Le site public n'est pas migré dans cette PR.** `website/` installe
    `react-resource-view` depuis npm et la CI le construit à chaque PR : migré
    maintenant, il casserait jusqu'à la publication de la 1.0. Les 9
    ressources du playground migrées sont dans
    `cli/__fixtures__/playground/after/` (sortie exacte du codemod,
    type-checkée) ; après publication : bump de `website/package.json`, puis
    `npx react-resource-view migrate website/src`, puis les pages de doc
    (extraits de code dans des chaînes, que le codemod ne voit pas) et
    `HomeBuilder`.
14. **Pas de skill `react-resource-view` publiée** : `skills-lock.json` ne
    contient que `archify`, il n'y avait donc pas de section « migrer de 0.x à
    1.0 » à ajouter.

## 6. Ce qui reste discutable

- **L'export autorisé par défaut** : toute liste JSON-LD avec un `path`
  affiche désormais un bouton « Exporter ». C'est ce que demande le ticket ;
  un défaut `export: false` serait plus prudent pour les applications
  existantes (le codemod écrit `export: false` quand des permissions étaient
  déclarées, mais pas pour les ressources qui n'en déclaraient aucune).
- **Les permissions asynchrones cachent l'action tant qu'elles répondent** :
  pas de clignotement, mais une liste dont les règles sont lentes affiche ses
  boutons avec retard.
- **`afterSave: "close"` sur une page** ramène à la liste (nouveau).
- **`layout.items()` répond à `?variant=items`** ; un `itemViewOptionFactory({
name: "List" })` répondait à `?variant=list`. Le codemod n'ajoute pas
  `id: "list"` pour ne pas encombrer la sortie : un ancien lien retombe sur le
  premier layout. Même chose pour les variants sans nom (`column` → `board`,
  `card` → `cards`, `item` → `items`).
- **Les tabs d'un `view.subViewResource` 0.x** (qui s'affichaient sous toutes
  les actions, liste comprise) sont posées sur `read` et `update` par le
  codemod.
- **`scope.home` et `scope.middleWare` ne sont lues par personne** : selon le
  principe 2 elles devraient disparaître, mais le ticket ne les vise pas.
- **Les messages de validation sont en anglais**, comme toutes les chaînes du
  paquet.

## 7. Ce qui gagnerait à évoluer côté `react-data-form` (hors périmètre)

- `FormInterface.inputs` est typé `Record<keyof Data | string, …>` : n'importe
  quelle chaîne passe, donc une faute de frappe dans un nom de champ n'est pas
  détectée. `react-resource-view` l'enveloppe (`FormDefinition`) pour proposer
  les champs de l'item ; le faire dans `react-data-form` profiterait à tous
  ses usages.
- Retirer un input hérité (`false`) et choisir/ordonner les champs (`fields`)
  sont des besoins de formulaire, pas de vue.
- `FormInterface.label.title/description` recoupe le titre des vues : deux
  endroits pour le titre d'un formulaire.
- Un `controller` typé selon la valeur du champ (`DatePickerInputController`
  sur une chaîne de date) éviterait des erreurs à l'exécution.
